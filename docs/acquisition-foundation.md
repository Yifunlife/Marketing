# 客户资料与获客来源基础结构

## 已上线的范围

客户资料页分为CRM客户（原21列）、获客线索与交接、平台接入三个区域。CRM原客户继续从CRM_DB只读读取，不能把历史CRM记录计作运营新增线索或本次交接回执。客户录入与业务维护仍在业务CRM完成。

运营人工线索保存到Marketing自己的D1 acquisition_leads，与业务客户库分开。只有用户录入的真实记录才写入，没有生产演示种子。当前所有平台的客户线索连接均为空；粉丝或广告指标已连接不能当作线索接口已连接。

## 来源和身份规则

- 原始平台、账号ID、账号名称、来源类型、广告/内容/表单/来源编号、平台线索ID、进入方式、接收时间不可通过维护接口覆盖。
- 平台+账号ID+平台线索ID建立唯一约束；人工缺少平台线索ID时使用明确标记manual:的表单请求ID防止重复提交，不伪装为平台提供的编号。
- 来源待核实 → 待关联CRM → 已关联CRM。来源核实必须有账号ID、来源编号和可复核依据；补充来源保存在verified_source和审计记录中，保留原始值。
- 核实是人工核实，不等于官方平台归因验收；budget_eligible始终为false，不供自动预算决策使用。
- 关联已有CRM客户前须由操作人查重、明确确认同一客户，服务端验证正式CRM客户存在。已有关联不能被改绑其他客户。多条咨询可以分别关联同一CRM客户，保留各自来源。
- 关联属于人工关联已有客户，不伪称已调用平台自动交接或收到CRM创建回执。不自动创建CRM客户。
- acquisition_events记录接收、来源人工核实、CRM关联的原始事件和操作者；接收与其审计事件在同一D1批次写入，重复投递不覆盖记录。

## 权限与接口

目前仅主管理员且无需改初始密码时可访问。所有请求沿用运营系统登录、同源写请求校验，无公共数据接口、无客户联系方式外传。GET/POST /api/acquisition；GET /api/acquisition/:id；POST /api/acquisition/:id/verify；POST /api/acquisition/:id/link。未开放其他修改、删除、平台连接或自动CRM创建接口。

新增结构使用迁移0003_acquisition.sql，仅修改Marketing数据库，不修改业务CRM数据库。附件后续仍使用R2，不在客户表存文件。

## 后续逐平台验收

确认主体与账号ID → 官方授权 → 核对可读线索字段和原始ID → 一条真实线索 → 重复读取不重复建客户 → CRM接收及跟进结果 → 来源归因验收。未通过前平台卡片保持待接入。未来适配器必须验证来源完整性，不使用人工录入接口冒充自动采集。

验证：权限、来源依据、原始信息保留、去重和跳过来源检查被拒绝的测试；另在本地SQLite运行接收、重复投递、核实、关联和三条审计记录的完整流程。正式库未写入测试线索。
